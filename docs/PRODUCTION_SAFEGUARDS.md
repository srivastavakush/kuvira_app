# Production safeguards and release setup

Implemented in this change:

- PayU hash uses the documented Hosted Checkout field sequence. Invalid callbacks cannot mutate transactions. Gateway reconciliation validates amounts; successful state is monotonic. Failed/expired reservations release inventory in the same Mongo transaction. Late success on a cancelled reservation is marked `requires_review` / `refund_status=review_required`, without confirming a conflicting booking.
- Booking uniqueness is now limited to `slot_active=true`. Startup creates the active index before removing the previous unconditional index and migrates historical cancelled records. Deploy during a maintenance window: stop older API revisions writing bookings until the migration and new revision are ready. Back up Mongo first. Duplicate active data makes migration fail rather than silently dropping records.
- Paid booking, stock and tournament reservation operations require MongoDB replica-set transactions (Atlas supports these). Pending checkouts have a 20-minute window. Reconciliation runs outside browsing/checkout requests so provider outages do not stall discovery. Unknown/unavailable provider verification retains reservations; maintenance retries. A late successful payment is escalated for manual review. Stock is deducted when reserved and returned on failure/expiry. Tournament seat allocation serializes on the tournament document and rejects duplicate registrations.
- User cancellation inquiries are accepted at least four hours before the start, using IST for timezone-less dates. Tickets persist and email `contact@kuvirasports.com`. Tickets do not automatically cancel/refund. Admins can respond in-app and update the ticket. Actual approved refunds remain a payment-provider operation; never mark a bank refund complete just because a ticket was resolved.
- Public privacy, terms, cancellation, community and deletion pages are available at `/policies/privacy`, `/policies/terms`, `/policies/cancellations`, `/policies/community`, `/policies/deletion`. Source copies are in docs/policies. Publish these under the real web domain and review operating entity/retention details before using in store declarations.
- Community posting requires policy acceptance. Users can report and block; platform admins review content and hide/dismiss reports. Blocked community authors are filtered server-side in either direction. Unblock is available in Help & Privacy.
- Account deletion disables API access immediately, queues removal of profile/media/community/coaching data and Firebase identity, and deactivates memberships. Financial and dispute records remain as described in the policy. Worker failures retry. This is an asynchronous request, not a claim of immediate erasure. External deletion requests can be emailed without installing the app.

## Mandatory deployment configuration

1. Run the maintenance loop continuously using `python -m maintenance`. The AI worker also starts it as a background task. A Cloud Run worker must remain running with CPU allocated outside requests; a web service that scales to zero cannot provide timely cleanup/reconciliation. Configure a liveness monitor and alert on overdue deletion tickets / email delivery.
2. Set transactional SMTP credentials via Secret Manager: `SMTP_HOST`, `SMTP_PORT=587`, `SMTP_FROM`, `SMTP_USER`, `SMTP_PASSWORD`. Delivery uses STARTTLS. Without SMTP, tickets remain visible as pending and users can use the email button. Test actual mailbox delivery; this environment does not send test emails to customers.
3. PayU: set `PAYMENT_PROVIDER=payu`, `PAYU_MODE=live`, merchant key/salt and the actual HTTPS callback base. Configure provider webhook delivery and test failure, abandonment, duplicate callback, delayed success and refund handling in staging first.
4. Direct video upload requires GCS and service-account permission to create resumable sessions, read object metadata and delete objects. Private resumable URLs are bearer capabilities: do not log them or put them in public documents. No signing key is sent to the frontend.
5. Configure GCS bucket CORS for your exact public web origins. Allow PUT and expose `Range`, `Content-Range`, and `Content-Type`; test the actual browser flow. Native upload has no browser origin. Keep the bucket private.
6. The default limit remains `AI_COACH_MAX_VIDEO_MB=500`. Uploads go directly to GCS in 8 MiB chunks. Native files are sliced from the selected file; API memory/temp disk does not hold the video. Vertex reads the private GCS URI. Successful analysis persists derived data then deletes source footage; reports remain rebuildable from derived data. Failed cleanup retries through maintenance. Failed/abandoned source objects are eligible for cleanup after seven days when no active job uses them. GCS soft-delete/versioning can retain deleted bytes: align bucket settings and privacy/retention disclosures with your actual deployment.
7. Raising `AI_COACH_MAX_VIDEO_MB=2048` enables a maximum of 2 GiB in the API and UI, but requires a real native/browser upload and Vertex-duration/model-quota test before rollout. Device picker/iCloud may still create a local device copy. This change avoids server-side full-video staging; it cannot guarantee the device/provider makes no copies.
8. Existing Firebase release blockers remain: native config files/plugins, production auth/API environment, signing fingerprints and live OTP verification. Do not publish a mock-auth build.

## Release tests

Typecheck, frontend regression checks and backend unit/dependency tests are run locally. These do not certify Atlas transaction isolation, SMTP delivery, GCS CORS/resumable behaviour, native picker behaviour or PayU settlement against real providers. Exercise those on staging before production. Policy wording and bank/refund operating procedures need operator review.
